# Move decisions into code, keep prefixes stable

The best tweaks for both Deep modes on `gemma4:e4b` add no new model calls. They take decisions the 4B model is bad at (first search, opening the original, when to stop, which evidence to cite) and make them in deterministic code. They also stop the agent loop from throwing away Ollama's prefix cache every turn, so several of them should *cut* wall-clock time and leave room inside the 1.2x budget for the one or two that add a call. For **Deep chat**, the top five, ranked by gain per latency, are: append-only context management (sticky nudge, trimming in large steps), a scripted pre-flight search, a code-built evidence ledger, synthesis from that ledger in a fresh short prompt, and code-side citation checks in the gate. For **Deep research**, the vendored graph has silent failures that matter more than any prompt tweak. ChatOllama ignores the `*_max_tokens` knobs and sends no `num_ctx`. Ollama truncates instead of raising, so upstream's overflow handling never fires. And a supervisor reply in prose ends research with empty notes. The fixes are a Modelfile alias that pins context and output length, tighter budgets (especially `max_content_length`), stricter failure detection in the wrapper, and citation checks after the graph. All of these fit the rules that `src/vendor/` stays unedited and every prompt lives in `src/prompts.py`. Moving to `qwen3.8:27b` (Q4_K_M, about 18 GB, 32K context in about 20 GB on one RTX 4090) mainly buys tool-call and instruction-following reliability. That lets the 400-char trimming, early nudges and fixed thresholds be relaxed. The cost is decode roughly 3.5x slower than E4B and very verbose default thinking, so it does not fit the 1.2x budget unless reasoning effort is capped. Nearly every expected gain below is extrapolated from 3.8–8B or larger-model studies. No public benchmark covers Gemma 4 E4B as an agentic RAG driver, so each item has to be A/B-tested on `data/KI`.

## E4B fails at choosing and starting tools, not at reading

The case for moving decisions into code rests on where small models fail. Gemma 4 E4B reads well: in thinking mode it scores **RULER 95.2 at 32K** and MMMLU 76.6, above Gemma 3 27B ([Gemma 4 tech report](https://arxiv.org/pdf/2607.02770); [model card](https://ai.google.dev/gemma/docs/core/model_card_4)). It is a weak agent: **Tau2 averages 42.2%**, against 68–77% for the 26B and 31B siblings ([model card](https://ai.google.dev/gemma/docs/core/model_card_4)), and an independent evaluation reports 26.0% ([computeprices](https://computeprices.com/models/gemma-4-e4b)). It is also weak at telling many similar passages apart, with **MRCR 8-needle at 128K of 25.4**. That is exactly the multiple-versions-of-a-law situation this wiki holds. In Docker's 21-model local evaluation, the predecessor gemma3:4B reached a tool-selection F1 of only 0.733, against 0.933 for qwen3:8B. The failure modes were wrong tool choice, bad arguments and **ignoring tool responses** ([Docker](https://www.docker.com/blog/local-llm-tool-calling-a-practical-evaluation/)). A 24B model made *no* tool calls on a long multi-criterion prompt but called tools correctly on a short one, which reads as reluctance to start retrieval rather than missing skill ([arXiv 2606.09916](https://arxiv.org/pdf/2606.09916)). Context length also hurts: all 18 models in Chroma's study degraded with input length far below their limits, and Qwen3-8B began looping at about 5,000 words ([Chroma, Context Rot](https://www.trychroma.com/research/context-rot)). Anthropic's guidance points the same way: minimal, non-overlapping tool sets, tool-result clearing as the "safest lightest touch" compaction, and fixed workflows wherever the task is predictable ([Anthropic, context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); [Building effective agents](https://www.anthropic.com/research/building-effective-agents)). Full plan-then-execute is not the answer. With GPT-4o-mini it scored **0.45 vs 0.62 for ReAct** ([GoalAct](https://arxiv.org/pdf/2504.16563)). The design target is therefore ReAct with code-scripted rails, not a new agent architecture.

## The current loop defeats Ollama's prefix cache, the biggest latency lever

Gemma 4's chat template places the system text first, then all tool declarations, then the conversation. Its sliding-window layers keep only the last 512 tokens, so llama.cpp cannot roll back to a divergence point earlier in the prompt. In one measured case, **one changed word at token 1,009 of a 2.9K prompt reused zero cached tokens**. An edit at the end of a ~5K system text forced re-prefill of ~14K tokens of tool schemas, taking ~45 s instead of seconds. A divergence just *after* the system prompt reused all of it ([AMD GAIA #5289](https://github.com/amd/gaia/issues/5289)). That result is measured, but on llama.cpp. Whether Ollama's engine behaves the same for Gemma 4 is not documented, though Ollama has been seen reusing ~19K prefix tokens per turn with append-only traffic ([scratchy #328](https://github.com/AI-native-Systems-Research/scratchy/issues/328)).

Reading `src/chat_agent.py` against this shows three cache breakers (inferred from the code, not measured). First, `_fit_window` recomputes a trimmed *view* on every turn and cuts the oldest bulky tool results to 400-char heads only until the history just fits. Once the window is full, almost every new turn trims one more early message, so the prompt changes in the middle on each step. Second, the wrap-up nudge from `NUDGE_AT` is appended to the view, not stored in state. Each turn's nudge therefore disappears and is replaced by that turn's AI and tool messages, and the divergence point sits more than 512 tokens back once the model has generated its reply. Third, `ChatOllama` is built without a `reasoning` setting. If thinking content is produced and dropped from history, that alone forces re-prefill (#5039 in [GAIA #5289](https://github.com/amd/gaia/issues/5289)). Toggling thinking per turn would also flip the `<|think|>` token at the very start of the system prompt ([Unsloth](https://unsloth.ai/docs/models/gemma-4)) and invalidate everything.

The fixes are cheap and come first because they *pay* for later tweaks. Trim with hysteresis: when the budget is exceeded, cut down to about 60% of the window in one pass, so the prefix then stays stable for many turns. Write the nudge into state once, as a stored message, instead of re-adding it to the view. Pin `reasoning` explicitly and keep it fixed for the whole run. Keep the system prompt and the bound tool list byte-identical within a run, with any query-specific hint going at the tail. Google's advice to keep thinking from tool-call turns in history ([model card](https://ai.google.dev/gemma/docs/core/model_card_4)) helps here too. Measure the effect with Ollama's `prompt_eval_count` and `prompt_eval_duration` per turn. The expected outcome is a lower turn latency once the window is full, but that is unmeasured on this box.

Two settings deserve an A/B test rather than a change. The loop runs at `temperature=0.3`, while Google, Ollama and Unsloth all recommend **1.0 / top_p 0.95 / top_k 64 for every use case** ([model card](https://ai.google.dev/gemma/docs/core/model_card_4); [Unsloth](https://unsloth.ai/docs/models/gemma-4)). On thinking, an Ollama maintainer reports that small models "often perform better on tool calling with reasoning enabled", and E4B with `think:false` tended to ask clarifying questions instead of calling tools. The cost was **about 2–4 s extra per turn** ([Ollama #15539](https://github.com/ollama/ollama/issues/15539)). Over a 20–40-step loop that is 40–160 s, which can by itself use up the 1.2x budget. Thinking-on therefore only fits if the cache fixes and shorter runs recover the time.

## Deep chat: ten code-side tweaks ranked by gain per second

The ranking below combines the evidence above with what each change costs in latency. "Measured basis" names the study a tweak is extrapolated from. None of them was measured with E4B in this loop.

| Rank | Tweak (where) | Added latency | Measured basis vs inference |
|---|---|---|---|
| 1 | Append-only context: trimming with hysteresis, nudge stored in state, `reasoning` pinned (`chat_agent.py`) | Negative (fewer re-prefills) | Cache mechanism measured on llama.cpp ([GAIA #5289](https://github.com/amd/gaia/issues/5289)); effect on Ollama inferred |
| 2 | Scripted pre-flight: code runs `raw_search` and `wiki_search` on the query and injects the top deduplicated hits as the first tool results (agent loop start) | ~0–5% (retrieval only) | Targets measured initiation and selection failures ([arXiv 2606.09916](https://arxiv.org/pdf/2606.09916); [Docker](https://www.docker.com/blog/local-llm-tool-calling-a-practical-evaluation/)); gain inferred |
| 3 | Evidence ledger: after each `raw_read`, code picks the 3–5 best-matching sentences or § clauses (BM25 or the existing cross-encoder), with file and § anchor, and keeps them at the context tail | ~0 (ms) | Extractive compression holds quality at ~6% of the tokens ([RECOMP](https://arxiv.org/pdf/2310.04408)); start and end positions are used best ([Liu et al.](https://arxiv.org/abs/2307.03172)) |
| 4 | Synthesis from the ledger in a fresh short prompt (promote the fallback-from-notes path to the default), outline-first with `[n]` citations | ~0 (shorter prefill) | Focused ~300-token prompts beat full 113K ones for all 18 models ([Chroma](https://www.trychroma.com/research/context-rot)) |
| 5 | Citation checks in `_submit_chat_impl`: every `[n]` exists, its source was opened, and any quoted span matches the source (normalised substring); one repair pass on failure | +0–10% (only on failure) | NLI citation checks agree with humans only 78–85% of the time ([ALCE](https://arxiv.org/pdf/2305.14627)); string matching is deterministic but does not verify paraphrased claims |
| 6 | Hit hygiene in `raw_search`: a reranker-score floor plus a relative cutoff, dedup by file and §, ±1 neighbour chunk stitched to each hit | ms | Even one related distractor lowers accuracy ([Chroma](https://www.trychroma.com/research/context-rot)); small-to-big raised faithfulness 95.7 → 96.7 ([Wang et al.](https://arxiv.org/html/2407.01219v1)); the thresholds must be fitted locally |
| 7 | Auto-read: if the top original is not opened by step ~3, code calls `raw_read` on its section | +1 read, no LLM call | Targets the measured "ignores tool responses" failure; gain inferred |
| 8 | Coverage-based nudge and stop: nudge when the gate counts are met; force synthesis after k steps with no new ledger entry | Negative | Practitioner reports of retrieval thrash and tool storms ([TDS](https://towardsdatascience.com/agentic-rag-failure-modes-retrieval-thrash-tool-storms-and-context-bloat-and-how-to-spot-them-early/)); inferred |
| 9 | Fixed-field tool output (`[3] file \| § \| score \| excerpt`) and explicit `ERROR:` lines; snake_case, string-only tool arguments | 0 | Error-as-content cascades ([SoK, arXiv 2603.07379](https://arxiv.org/pdf/2603.07379)); avoids Gemma 4 parser bugs [#18354](https://github.com/ollama/ollama/issues/18354), [#18390](https://github.com/ollama/ollama/issues/18390) |
| 10 | Contextual chunk headers (`title › § path`) added to FTS5 and embedding text at index time | 0 at query time; needs an index rebuild | −35% to −49% top-20 retrieval failures with LLM-written context ([Anthropic, contextual retrieval](https://www.anthropic.com/news/contextual-retrieval)); the deterministic header variant is untested |

Items 2, 3 and 4 work as a unit. Pre-flight removes the first-move failure and already counts toward the "≥3 searches" rule. The ledger turns long `raw_read` results into anchored quotes, so their full text can be trimmed sooner without losing facts. And synthesis from the ledger means the final answer never has to dig through a 30K-character history in which, by Chroma's evidence, a 4B model degrades. The `think_tool` notes currently carry facts across trimming. The ledger does the same job without depending on the model writing good notes, so `think_tool` could later be dropped from the tool menu. That follows Anthropic's smaller-tool-set advice, but it needs its own A/B test.

Two items reshape the quality gate rather than add to it, and both are inferences that need a test. The flat **≥500-word minimum** has no evidence either way, since no study measures what a length floor does to faithfulness. From first principles, though, a floor makes a small model pad when evidence is thin, and padding is where uncited sentences come from. The 43.1% response-level hallucination rate in RAGTruth gives a sense of the base rate ([RAGTruth](https://arxiv.org/pdf/2401.00396)). An evidence-proportional floor, about 80–120 words per distinct cited source, or counting only cited sentences, rewards coverage over verbosity. Likewise, "≥3 searches" can be met with three paraphrases that `run_memory` does not block. "Every sub-question has ≥1 ledger quote" measures the thing the counter stands in for. The project rule that a wiki-only answer is rejected stays as it is in either variant.

Query-side LLM rewrites are mostly not worth the time. In the one controlled benchmark, plain **query rewriting lowered nDCG@10 from 70.2 to 67.9 and decomposition to 66.1**, at 3–6x the retrieval latency. **HyDE raised it to 75.4**, and one pseudo-document beat eight at half the cost ([Wang et al., EMNLP 2024](https://arxiv.org/html/2407.01219v1)). Those runs used 7B and GPT-3.5-class generators, so a HyDE passage written by E4B may be weaker. HyDE is worth a single A/B slot inside pre-flight: one short generation of about 1–3 s per question, not per step. The existing GGUF cross-encoder is already the right call. A 220M monoT5 reached MRR@10 31.8 against 32.4 for a 7B reranker, at **4.5 s vs 82.4 s** ([Wang et al.](https://arxiv.org/html/2407.01219v1)).

## Deep research: fix the silent failures before tuning quality

The vendored `open_deep_research` (pinned at `d337ae32`; upstream is now archived) has failure paths that a 4B model on Ollama reaches easily. All of them can be fixed from `src/deep_research_agent.py`. Reading the code shows that **ChatOllama leaves `num_predict` and `num_ctx` unset** when it gets `max_tokens`. So `DEEP_RESEARCH_MAX_TOKENS` does nothing, and the graph runs at the daemon's default context. The pinned daemon (`src/ollama_server.py`) does not set `OLLAMA_CONTEXT_LENGTH`. Ollama's default depends on VRAM: **4K under 24 GiB, 32K from 24–48 GiB** ([Ollama docs](https://docs.ollama.com/context-length)). A 24 GB RTX 4090 sits right on that boundary, so `ollama ps` during a Deep run should show which applies. Because the rest of the app sends `num_ctx=32768`, and a different `num_ctx` makes Ollama reload the model, Deep research calls may also force reloads when they alternate with app calls. The other failure paths are confirmed bugs in the vendored code. In `supervisor_tools`, an `or True` (bug [#283](https://github.com/langchain-ai/open_deep_research/issues/283)) makes *any* child-researcher exception end research as if it had succeeded. A supervisor reply with no tool call ends research immediately with empty notes. Three failed compressions turn the finding into the string "Error synthesizing research report: Maximum retries exceeded". And because Ollama truncates prompts silently instead of raising, `is_token_limit_exceeded` never fires ([README](https://github.com/langchain-ai/open_deep_research); [code at the pinned commit](https://github.com/langchain-ai/open_deep_research/blob/d337ae32ed4ff8f4c6fbe192ba3bf1b2d6610799/src/open_deep_research/deep_researcher.py)).

| Rank | Tweak | Mechanism (rule-compliant) | Added latency |
|---|---|---|---|
| 1 | A Modelfile alias of `gemma4:e4b` with `num_ctx 32768` (equal to `INGEST_NUM_CTX`, so no reload) and a `num_predict` cap, passed as `ollama:<alias>`; or `OLLAMA_CONTEXT_LENGTH` set in the pinned daemon's environment | Configuration / `ollama_server.py` | 0; prevents truncation and reloads |
| 2 | Wider failure detection in the wrapper: empty `notes` or `raw_notes`, the compression error prefix, the report error prefix, or too few distinct URLs that also appear in `raw_notes` all mean a fall back to Quick | Wrapper | 0 |
| 3 | `max_content_length` 50,000 → 12,000–20,000 characters | Configuration | Large reduction: summaries make up most of the LLM calls |
| 4 | Budgets: concurrency 1 (the daemon runs `NUM_PARALLEL=1` anyway), `max_researcher_iterations` 2–3, `max_react_tool_calls` 4–5, `max_structured_output_retries` 4–5 | Configuration (`DEEP_RESEARCH_*`) | Shorter; retries cost time only on failure |
| 5 | Post-graph citation check: keep only cited URLs present in `raw_notes`, check numbers and salient tokens against that URL's summary, renumber `### Sources` | Wrapper, no LLM | ~0 |
| 6 | Cross-researcher URL dedup when `raw_notes` are reused (upstream dedups only within one call) | Wrapper | 0 |
| 7 | A narrower question: `DEEP_RESEARCH_QUESTION` asks for at most 2–3 one-line sub-questions | Prompt in `prompts.py` | Shorter |

The summarisation step is the dominant latency term. The vendored `tavily_search` hard-codes `include_raw_content=True` and `max_results=5`, then runs one LLM summary per URL with a 60 s timeout that silently falls back to a snippet ([utils.py](https://github.com/langchain-ai/open_deep_research/blob/d337ae32ed4ff8f4c6fbe192ba3bf1b2d6610799/src/open_deep_research/utils.py)). Higher concurrency on a `NUM_PARALLEL=1` daemon just queues more of those calls into the timeout. Cutting `max_content_length` is the only lever on this that needs Configuration alone. A stronger option is to set `search_api="none"` and supply a local MCP `web_search` tool that calls Tavily with `chunks_per_source=3` and `include_raw_content=False`. That returns verbatim, relevance-ranked chunks with no LLM summary ([Tavily API](https://docs.tavily.com/documentation/api-reference/endpoint/search)), removing about five LLM calls per search step and replacing abstractive paraphrase with quotes. The project should decide on it explicitly. It is Configuration-reachable, but it adds a local process; `load_mcp_tools` may only support HTTP transport, which was not verified; and its output must keep the `URL:` line format that citation parsing depends on. Monkeypatching `tavily_search_async` would also work but goes around the vendoring rule, so it should not be done without the user's approval.

For report quality, the best small-model results on Deep Research Bench come from **outline-first, section-by-section writing over a curated evidence memory**. WebWeaver (Qwen3-30B-A3B) reaches 46.77 RACE with the best FACT citation scores ([WebWeaver](https://arxiv.org/html/2509.13312v3)). The 8B AgentCPM-Report reaches 50.11 RACE, and even prompt-only WARP on a 235B model beat plan-then-write, 50.72 vs 49.90 ([AgentCPM-Report](https://arxiv.org/html/2602.06540)). Those are trained models, so the numbers do not transfer to a prompted 4B model. The pattern can still be built in the wrapper after the graph: one section per research unit, each written only from that unit's evidence blocks, with `[URL]` citations mapped in code. Upstream's single-shot `final_report_generation` cannot be skipped via Configuration, so this adds N section calls on top of it. It fits the 1.2x budget only as a selective repair, regenerating just the sections whose citations fail the check in tweak 5. Upstream's own data shows the research role matters most: swapping only that model moved RACE from **0.4309 to 0.4943** ([README](https://github.com/langchain-ai/open_deep_research)). With E4B, though, the binding constraint is whether the supervisor calls `ConductResearch` at all. Measuring that rate is the first diagnostic to run.

## Qwen3.8-27B buys reliability at roughly 3.5x slower decode

`qwen3.8:27b` is an official Ollama tag: **18 GB, 256K context, tools and thinking** ([Ollama](https://ollama.com/library/qwen3.8)). It is a dense hybrid with 48 Gated DeltaNet layers and only 16 full-attention layers, which have 4 KV heads ([HF card](https://huggingface.co/Qwen/Qwen3.8-27B)). From the card's dimensions, the KV cache works out to about **64 KiB per token at F16, or ~2 GiB per 32K** (inferred). Measured VRAM on an RTX 4090 at Q4_K_S is **20 GB at 32K and 22 GB at 64K** ([Hardware Corner](https://www.hardware-corner.net/qwen3-8-27b-hardware-tests/)). So the project's current `num_ctx=32768` fits unchanged on one card, and 64K is tight but feasible with F16 KV. Q4_K_M showed "no noticeable difference from BF16" on GPQA, IFBench and Terminal-Bench, while Q2 dropped clearly on Terminal-Bench ([Quesma](https://quesma.com/blog/qwen38-27b-quantizations-benchmarked/)). Q6_K (~22–23 GB) leaves almost no room for context, and Q8_0 does not fit. KV-cache quantization is reported to be more sensitive, so F16 KV is the safe default up to 64K. The card publishes **IFBench 79.5** (E4B: 38–44) and GPQA 89.2 (E4B: 58.6), plus strong agentic proxies such as WebArena-Verified 64.8 ([HF card](https://huggingface.co/Qwen/Qwen3.8-27B)). It gives no BFCL, tau2 or RULER numbers, so the tool-use gain is strongly implied but not measured.

The cost is speed. On a 4090, llama.cpp at Q4 decodes at **46 tok/s at 4K and 38 tok/s at 64K** ([Hardware Corner](https://www.hardware-corner.net/qwen3-8-27b-hardware-tests/)). This box measured E4B at **164 tok/s on the pinned Ollama daemon** (`docs/gpu.md`), so decode is about 3.5x slower. Prefill stays cheap at about 2,400 tok/s at 32K. The model is also very verbose: it used **200M output tokens on Artificial Analysis's index, against a median of 82M** ([Artificial Analysis](https://artificialanalysis.ai/models/qwen3-8-27b)), and the default `reasoning_effort=xhigh` spends about 8K thinking tokens per GPQA question. A 40-step loop at xhigh would take tens of minutes. At the 1.2x budget, the 27B only works with `reasoning_effort` low or medium on tool turns, and that budget probably cannot be met in Deep chat at all. Fewer steps help: a more reliable model should need far fewer than E4B's 20–40 iterations, which is the hypothesis to measure. MTP self-speculation gives +60–80% decode in llama.cpp ([hackmd](https://hackmd.io/@thc1006/qwen3-8-27b-speculative-decoding-rtx-3090)), but Ollama support is unconfirmed. Moving to raw `llama-server` would conflict with the "reach models via `ollama_client.host()`" rule and needs a design decision. E4B cannot serve as a draft model, because the tokenizers differ.

What the 27B enables is mostly *relaxing* E4B crutches, each after telemetry shows it is no longer needed. Tool-result trimming can go from 400 characters to whole sections. `RAW_READ_CAP` can rise from 16 KB to 32–64 KB, with a 64K context, which makes real multi-document comparison possible. Nudges can fire later, and the fixed word and search counts can become soft hints. A self-verification pass over the draft becomes affordable. In Deep research, `with_structured_output` and the supervisor's tool calls should become reliable, so the empty-notes path should rarely trigger. Several guards stay, because they are correctness rules rather than small-model crutches: the original-document gate in `_submit_chat_impl`, `run_memory` duplicate blocking, code-side language pinning, and the citation checks above. Two risks need checking before any switch. Ollama's earlier Qwen3.5-27B support mapped the model to the wrong (Hermes) tool-call parser ([ollama #14493](https://github.com/ollama/ollama/issues/14493)), and qwen3.8 tool-call issues were reported open in October 2026 ([Betterclaw, issue numbers unverified](https://www.betterclaw.io/blog/qwen-3-8-27b-tool-calling-fails-agents-fix)). Also, `preserve_thinking` is on by default and grows the context. The appealing role split (27B for supervisor and final report, E4B for summarization and compression) is not Configuration-only on this box. Two models at 18 + ~9.5 GB do not fit one 24 GB card with context. The vendored `init_chat_model("ollama:…")` takes its host from the single `OLLAMA_HOST` that the wrapper sets. And the second 4090 may serve other apps (`docs/gpu.md`). So the split needs a per-role host design and a free second card. The 27B is still the stronger choice for Deep research's final report, which is a single long synthesis call with no tool calls, where its long-context and instruction-following advantage counts most per decoded token.

## A/B test plan on `data/KI`

Everything above that is not marked as measured is extrapolated, so the next step is a fixed question set on `data/KI`. It should cover German and English questions, single-§ and multi-version questions, and one question where the answer is "not in the corpus". Run each variant at least three times, since temperature is non-zero. For Deep chat, log wall-clock time, iteration count, per-turn `prompt_eval_count` and `prompt_eval_duration` (which shows cache hits directly), the gate rejection rate, distinct opened originals, citation-verification pass rate, and a sampled human faithfulness check. For Deep research, log the share of runs where the supervisor executed at least one `ConductResearch`, the compression-error rate, distinct verified URLs, and the share of cited URLs absent from `raw_notes`. Test in this order: the append-only context fix alone, which should show a lower `prompt_eval_count` after the window fills; then pre-flight plus the ledger; then ledger synthesis plus the citation checks. Separately, test temperature 0.3 vs 1.0 and thinking on vs off, and the Modelfile alias plus `max_content_length`. A variant is accepted if it holds or improves the faithfulness and citation metrics and stays within 1.2x of today's median wall-clock time.

## Conclusion

For a 4B model the cheapest quality gain is often the one that saves time, which runs against the usual trade-off. Today's loop rebuilds its own prompt in a way that, by the code reading above, throws away the KV cache once the window fills. And Deep research runs at a context length it never sets. Fixing those two plumbing issues comes before any prompt engineering, and it creates the latency headroom that thinking mode or HyDE need. The design principle carries over unchanged to the 27B: code decides the first move, picks the evidence and verifies the citations, and the model writes. With the 27B the model can then be trusted with more steps in between, but not with grounding, which stays enforced in code.
