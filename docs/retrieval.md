# Retrieval

> Split out of [architecture.md](architecture.md) on 2026-07-24 (that file was over the
> 35 000-char documentation budget). Architecture keeps the three-layer knowledge model
> and the non-retrieval modules; everything about *finding* things lives here.

Retrieval runs in three signals, each optional above the first and each degrading to the
one below it, so no layer can regress the layer beneath:

| Arm | Module | Stage | Degrades to |
|---|---|---|---|
| Lexical BM25 (FTS5) — the citation source of truth | `src/lex_index.py` | B | — (always present) |
| Semantic cosine over local embeddings | `src/embed_index.py` | C | lexical only |
| Cross-encoder rerank | `src/rerank.py` | D | plain RRF fusion |

`src/retrieval.py` is the single entry point that composes them. `search(q, top_k, scope,
use_rerank=False)` fuses arms A+B by weighted RRF and optionally applies the Stage D
reranker; `use_rerank` splits Fast (browsing, per-keystroke — fusion only) from Deep
(answer paths that commit to a citation — full pipeline).

## Retrieval modules

- **`src/chunker.py`** structural chunker. `split(text)` returns a list of `{chunk_id, anchor, heading_path, char_start, char_end, text, lang}` dicts using one of three strategies: legal `§` headers, markdown `##`/`###`, or paragraph windows with overlap. `chunk_id = sha256(normalized)[:16]` is content-addressable so re-ingest is idempotent and diffable. `write_chunks()`/`load_chunks()`/`all_chunks()` persist to `data/chunks/<source-slug>.jsonl`.
- **`src/lex_index.py`** Lexical index over chunks, stored as a single SQLite **FTS5** table (`data/<DB>/index/chunks.sqlite`) that holds the pre-expanded variant token stream in an indexed `terms` column and supplies `bm25()` scoring. `build(chunks=None)` does a full rebuild; with no args it indexes raw source chunks (`scope="raw"`) **plus** wiki page pseudo-chunks (`scope="wiki"`, R-1) generated by `wiki_chunks()` (each page body, prefixed with its title + filename stem, split via `chunker`; text stored inline since these aren't in `data/chunks/`). For single-source changes, **incremental** helpers keyed on the `source` column avoid a corpus rebuild: `index_replace_source(source, chunks)` (delete + insert that source's rows), `index_replace_wiki_page(name)`, and `index_delete(source)` — ingest and `delete_source` use these. `query(q, top_k, scope=None)` expands the query to the same variants, MATCHes with an `OR` group, ranks by `bm25()`, and deduplicates by `chunk_id`; `scope` filters to `"raw"` / `"wiki"`; returns `[]` when the DB has no index yet. Because that empty return is indistinguishable from "no match", `index_health()` reports the per-scope row counts (`{raw, wiki}`, both `0` when `chunks.sqlite` is absent) so the UI can say *no index* instead of *no results* — databases last built before the FTS5 cutover (`d25fbe8`) have no store and need one **Maintenance → Search index → Rebuild** pass; `needs_rebuild()` (content but no indexed rows) lets `scripts/heal_indexes.py` do that pass for every shard when `scripts/run_app.py` starts the server. Each surface word is stored under up to four normalized variants — surface lower-cased, NFKD-strip (ü→u), umlaut digraph (ü→ue, ß→ss), and a light German+English suffix stem — so queries match regardless of writing style. No external NLP deps; built-in stopword list per language.
- **`src/gloss.py`** — pure acronym and gloss detection for the query vocabulary (below).
- **`src/embed_index.py`** — semantic (dense) arm (Stage C). Local, file-backed vector index over the **same** chunks `lex_index` indexes: per-DB `vectors.npy` (float16, L2-normalized rows) + `vectors.json` (embedding model + aligned row meta), embedded via the local Ollama `/api/embed` (`EMBED_MODEL`, default `bge-m3`) — no cloud API, no external vector DB/service. `query(q, top_k, scope)` is brute-force cosine (rows normalized ⇒ dot product), returning the **identical hit-dict shape** as `lex_index.query`. Wiki pseudo-chunks are embedded with a deterministic OKF identity prefix (`type/title/about/tags` via `okf.enrich_frontmatter`) so a page's own topic words boost chunks whose body omits them — the prefix affects the *embedded* text only, never `chunk.text`/anchors/citations. **Optional + graceful:** `available()` gates use (returns False with no vectors / on a model mismatch); the vectors are a pure derived cache rebuilt by `build()` / `scripts/backfill_embeddings.py`. Per-source **incremental** updates (`index_replace_source` / `index_replace_wiki_page` / `index_delete`, mirroring `lex_index`) keep an already-embedded DB current on ingest/delete — best-effort and gated on an existing model-matching index, so ingest never fails on embeddings and a never-backfilled DB never gets partial coverage. Context-overflow inputs are isolated + hard-truncated so one pathological chunk can't fail a whole build. No LangChain.
- **`src/retrieval.py`** — hybrid retrieval entry point (Stage C). `search(q, top_k, scope)` runs the lexical arm (always) + the semantic arm (when `embed_index.available()`) and fuses them with weighted Reciprocal Rank Fusion (RRF `k=60`, dense arm `2×`, top-rank bonus), keyed on `chunk_id`; the lexical hit wins ties so `matched_terms`/inline text survive. When the semantic arm is unavailable it returns exactly `lex_index.query(...)[:top_k]`, so enabling embeddings **cannot** regress the lexical baseline (the lexical arm stays the citation source of truth). Consumed by the chat/agent answer paths — `tools._raw_search_db`, `wiki_engine._candidate_pages_for_query`, `_gather_pages`. Ingest routing (`_select_affected_pages`) and the Explorer's `search_wiki` stay lexical (deterministic / per-keystroke). In a DB with an ontology, both `search()` and `search_wiki` add an **ontology arm** to the fusion (lexical hits within the sources of the works/classes a question names; [ontology.md](ontology.md) §Search); without one, or when nothing is named, results are unchanged. After fusion and rerank, hits from versions not in force at the question's point in time are moved to the end, never dropped ([ontology.md](ontology.md) §Time). `use_rerank=True` adds the Stage D cross-encoder pass and is set by exactly those three answer-path call sites; it deepens the fused list to `RERANK_CANDIDATES` before reranking down to `top_k`. No LangChain.
- **`src/rerank.py`** — cross-encoder reranker (Stage D). The third and last retrieval signal: where BM25 scores term overlap and the dense arm scores whole-passage similarity, a cross-encoder reads query *and* chunk together in one forward pass, so it can judge whether the passage actually answers the question. Runs `bge-reranker-v2-m3` (GGUF under `models/`, a re-downloadable artifact) **in-process** through `llama-cpp-python` — one optional `uv` extra, no second service, no cloud API. `rerank(q, hits, top_k)` scores the top `RERANK_CANDIDATES` (default 30) fused hits and blends *normalized* fused and reranker scores position-awarely — reranker share 0.25 at ranks 1–3, 0.40 at 4–10, 0.50 at 11+ — so retrieval is trusted at the head and the cross-encoder gets more say further down, without ever owning more than half the decision. **Fails open unconditionally**: missing GGUF, missing runtime, or any exception mid-scoring returns the fused order untouched (a down reranker must degrade ranking, never break search). Each hit carries `rerank_score`, the raw logit, which **Stage E** (`src/calibrate.py`) thresholds for abstention. **GPU (optional, ~30× faster):** by default the reranker runs on CPU (~350 ms/pair — the dominant latency in Deep chat, since every `raw_search` reranks `RERANK_CANDIDATES`). On an NVIDIA box, install the CUDA build + the CUDA **runtime** as userspace pip wheels — no system CUDA toolkit, no `sudo`: `llama-cpp-python` from the `cu125` index plus `nvidia-cuda-runtime-cu12` / `nvidia-cublas-cu12` / `nvidia-cuda-nvrtc-cu12`. `rerank._preload_cuda()` loads those `.so`s with `RTLD_GLOBAL` before importing `llama_cpp`, so `libcudart` resolves without `LD_LIBRARY_PATH`; `rerank.py` already offloads all layers (`n_gpu_layers = -1`). Measured **353 → 11 ms/pair** on 2×RTX 4090. Caveat: `uv sync --extra rerank` reinstalls the CPU sdist build (and needs `cmake`), so re-run the CUDA `llama-cpp-python` install after any sync. Three facts worth not rediscovering: (1) **Ollama cannot host a reranker** — no rerank endpoint, and a reranker driven through `/api/generate` returns uniform ~0.5 noise rather than erroring, so it fails silently; (2) `llama-cpp-python` does **not** expose `Llama.rank`, so scoring drives the ctypes layer and builds the cross-encoder input `[BOS] q [EOS] [SEP] doc [EOS]` itself under `LLAMA_POOLING_TYPE_RANK`, reading `llama_get_embeddings_seq()[0]`; (3) the project's prebuilt wheels are musl-linked despite a `linux_x86_64` tag and fail to import on glibc — install from sdist. No LangChain.
- **`src/calibrate.py`** — calibrated abstention (Stage E). Turns the Stage D `rerank_score` into a decision: `assess(hits, db)` reports `(confident, relevance, closest_hit)` and abstains (`confident=False`) only when a per-DB threshold τ exists **and** the best passage's raw logit is below it. τ is a per-DB **derived artifact** in `data/<db>/index/calibration.json`, calibrated offline by `scripts/calibrate_abstention.py` from the score separability of should-answer vs should-abstain fixtures (DECISION 8: per-DB, maintainer-visible, conservative default = the max-margin midpoint of the separating gap). `relevance()` is a temperature-scaled logistic (display only, never the decision). **Fail-safe:** no `calibration.json`, no `rerank_score` on the hits (reranker down / failed open), or `ABSTAIN_ENABLED=0` ⇒ `confident=True` — it never abstains on an uncalibrated score, so search reliability is never regressed. Consumed by the Deep answer paths only: `wiki_engine.query_with_sources` (deterministic — returns the abstain message and **skips** the LLM synthesis) and the Deep-chat submit gate `tools._submit_chat_impl` (a single bounded soft nudge to abstain, via `run_memory.best_relevance`). The per-keystroke nav search stays fusion-only and untouched. No LangChain.
- **`src/qa_gen.py`** ingest-time hypothetical-question generator (HyDE, lexical-only). `_select_target_chunks` ranks chunks (anchored > densest > longest > stable) and keeps the top `QA_MAX_PAIRS_PER_SOURCE` (default 5). One batched LLM call asks for 2–4 short questions per kept chunk; the output is sliced to the per-source cap. If the LLM returns nothing usable, retries once at a higher temperature; if still empty, emits one source-title fallback question. Persists `(chunk_id, question)` rows to `data/index/qa.jsonl`. `lex_index.build()` folds question tokens into the parent chunk's term frequencies (but not its doc length, so BM25 b-normalization stays honest). `delete_source_entries(name)` rewrites `qa.jsonl` in place, removing rows for the given source.

## Query dataflows

### Query

```
wiki_engine.query_with_sources(question)
  → _wiki_hits_by_page(question)                             # the one reranked wiki-scope search
  → _raw_hits(question)                                      # the one reranked raw-scope search
  → _candidate_pages_for_query(question, wiki_sources, raw_sources)  # Q-1 hybrid pre-select
      → those wiki hits  ∪  those raw hits → _source_to_pages()
      → linked_pages(top _QUERY_LINK_SEEDS)                  # + 1-hop link expansion
  → top 5 candidates in reranked order                       # no LLM call
      (ollama_client.generate(select prompt) over the full index only when nothing matched)
  → inject top _QUERY_CHUNKS_PER_PAGE wiki chunks per page   # Q-3 section-level, not full pages
  → _raw_excerpts: top _QUERY_RAW_EXCERPTS original passages, τ-gated, headed [Source: file §x]
  → calibrate.assess(wiki_hits, db) — Stage E gate                # abstain if best rerank_score < τ
      → if not confident: return abstain message, SKIP synthesis  # no answer from weak context
  → raw_sources = page frontmatter `sources` ∪ the quoted originals
  → ollama_client.generate(answer prompt + lang.response_directive(question), temperature=0.3)
      (generate_stream with on_token when the caller streams, as the Broadsheet Chat does)  # direct answer, then details; cites [page title] and [Source: …]
  → return {answer, sources (wiki filenames), raw_sources (original data/raw/ filenames)}
```

`app.py` Chat page and Wiki Explorer both render sources in a collapsible "Sources" expander (original `data/raw/` documents + related wiki pages).

### Abstention (Stage E)

The safety property: decline to answer rather than synthesize from weakly-matched context (idea.md §3.5). The decision keys on the **top passage's** raw cross-encoder `rerank_score` vs a per-DB threshold τ (`calibrate.assess`). τ is calibrated **offline** — never at query time, so abstention adds no latency and, on the abstain branch, *saves* the LLM synthesis call.

`scripts/calibrate_abstention.py --db <DB> [--write]` measures score separability against two fixtures — `bench/fixture_<DB>_chunk.json` (should-answer, labelled relevant chunk_ids) and `bench/fixture_<DB>_negatives.json` (should-abstain, out-of-domain) — using the top-hit `rerank_score` of each. It reports query-level ROC-AUC and writes τ = the max-margin midpoint of the separating gap to `data/<DB>/index/calibration.json`. **Kill criterion** (idea.md §5.10): poor separability ⇒ do not ship abstention for that DB. Measured on **KI**: query-level AUC **1.000**, τ **−4.14** (0 % false-abstain, 100 % correct-abstain on the fixtures). Each DB is calibrated independently; an uncalibrated DB simply never abstains (fail-safe). Re-run after changing `RERANK_MODEL` or `EMBED_MODEL`. Env: `ABSTAIN_ENABLED` (master switch), `ABSTAIN_TAU_DEFAULT` (fallback τ when no per-DB file).

### Query vocabulary (acronyms, glosses, ontology terms)

The user's word is often not the sources' word (*NORM* vs. *Rückstände*), and a small model
cannot bridge that gap itself. Three deterministic steps do it in code (memo
`ideas/deep-chat-norm-vocabulary-gap-and-plan-execute.md`, S1/S2b/S2c):

- **Acronym guard** (`lex_index.query`): the index is lowercase, so `NORM` used to match every
  "Diese Norm …" of a DIN standard. A capitalised word in a mixed-case query
  (`gloss.acronyms`) now counts only where the text writes it in capitals: those hits come
  first (best of `ACRONYM_FETCH` rows), the rest are ranked by the query without the acronym's
  forms. A lowercase query (`Norm`) still matches every spelling.
- **User gloss** (`gloss.find`): `NORM (natürliche Radioaktivität)` or
  `natürliche Radioaktivität (NORM)` pairs the acronym with the user's explanation. A search
  that uses the acronym — in the query itself or in the run's question (`run_memory`) — gets
  one more lexical list for the explanation, and the briefing states the meaning
  (`GLOSS_BRIEFING`).
- **Ontology terms** ([ontology.md](ontology.md) §Schema modules, `terms:`): a query word
  that is a term's `pref`/`alt` label adds a lexical list for `pref` + `expand`, and the
  briefing names the sources' word (`ONTOLOGY_BRIEFING_TERM`). An acronym label matches only
  as written.

`retrieval._vocabulary_lists` adds both lists to the RRF fusion of `search()` and
`ontology_rerank()` (`W_VOCABULARY = 1.0`): they add candidates and never remove one, and a
query without an acronym gloss or term is unchanged. `retrieval.vocabulary(q)` returns the
same words for Deep chat's in-file section ranking (`tools._run_query`), so a bare read of a
statute serves the sections in the sources' vocabulary, not § 1.

### Multi-database chat (search scope)

Wiki Chat can search several databases at once. Two separate concepts:

| | Holds | Set by | Drives |
|---|---|---|---|
| **Active DB** (`_active`) | one name | top-bar selectbox | every path getter; all writes (upload, ingest, `file_answer`) |
| **Search scope** (`_scope`) | list of names | Wiki Chat "Search in" multiselect | read-only retrieval fan-out |

Scope defaults to `(active_db,)`, so every single-DB caller is unaffected. The app resets it every rerun; Wiki Chat sets it from "Search in", Research to the reachable classification levels on opt-in, and Explorer/Maintenance to the one level they show. Entries are shard ids (`KI`, `KI@strict`), each checked by the classification gate ([security.md](security.md)).

Fan-out binds **one DB at a time** — path state is never merged:

```
for db in db_context.search_scope():
    with db_context.using_db(db):
        ...   # every getter now resolves to `db`
```

Consumers: `wiki_engine.query_with_sources` (Fast — one `_gather_pages` pass per DB, then a *single* synthesis call), `tools._wiki_search_one` / `_raw_search_one` (Deep), and `chat_agent._build_raw_index`.

**Cross-DB identity: `DB::file.md`.** Page names collide across databases (every DB has `index.md`), so results carry their origin. `db_context.qualify()` prefixes a name **only when the scope holds >1 DB** — single-DB citations, prompts, and run-memory keys stay byte-identical, so the common path carries no regression risk. `db_context.split_ref()` reverses it and falls back to the active DB when the prefix is absent or outside the scope, so a small model that drops or invents a prefix still reads a real file instead of erroring. Separator is `::` because `/` already means the `insights/` subpath and DB names may contain spaces (hence the permissive `_WIKI_CITE_RE`).

Three things that break subtly if changed:

- **Budgets are split, not multiplied.** `_QUERY_SYNTH_MAX_CHARS` (Fast) and each search tool's `max_results` (via `tools._per_db_budget`) are divided across the scope, with floors (`_QUERY_MIN_DB_SYNTH_CHARS`, `MIN_HITS_PER_DB`) so a wide scope doesn't starve every DB. N databases cost ~one database's context.
- **Run-memory keys are DB-qualified** (`tools.raw_read`). Keying on the bare filename would make `shared.md` in DB B look like an already-read duplicate of `shared.md` in DB A, and the guard would suppress the second read.
- **`_with_active_db` carries the scope, not just the active DB.** Worker threads don't inherit ContextVars, so a scope lost in the pool silently narrows a cross-DB search back to one DB.

Link traversal stays **inside** each DB — `related:` edges never cross databases. Writes stay single-DB: "Save answer to wiki" files into the active DB and keeps only that DB's pages as `related:`.

### Link-aware retrieval (`wiki_engine.linked_pages`)

How a query reaches connected material it never lexically matched. One deterministic primitive, `linked_pages(filenames, limit)`, returns 1-hop neighbours as `{filename, title, excerpt, via, kind}` and has two consumers: `_candidate_pages_for_query` (Fast chat — neighbours are appended to the BM25 candidate set, of which the top five in reranked order are answered from) and `tools._wiki_search_one` (both agents — neighbours are appended to search output as `[Wiki linked N]` entries, gated by `WIKI_LINK_EXPANSION`).

Two edge types feed it:

| `kind` | Source | Why |
|---|---|---|
| `link` | `related:` frontmatter, **either direction** | The explicit cross-reference the ingest LLM wrote. |
| `shared-source` | A common entry in two pages' `sources:` | Pages distilled from the same original are topically adjacent even when neither cites the other. |

**Traversal is undirected, and this is load-bearing.** `related:` is written at ingest, so a page can only cite pages that already existed: new pages point at old ones and old ones never gain back-links. In the real corpus ~88% of edges are one-way (Strahlenschutz: 102 distinct pairs, only 12 mutual), so following out-links alone makes exactly the central, oldest hub pages — the ones a query hits first — look like dead ends. `_backlink_map()` reverses `build_link_graph()` so in-links count too.

**Shared-source edges are clique-guarded.** A source backing many pages carries no topical signal (`StrlSchG.md` alone backs 25 pages, `BImSchG.md` 22), so `_shared_source_siblings()` skips any source feeding more than `_SHARED_SOURCE_MAX_CLIQUE` (8) pages rather than flooding results with "both mention the big law".

Ranking is tiered: explicit `link` edges outrank `shared-source` ones, then neighbours reached from more seeds win, with insertion order breaking ties (stable sort). Measured effect on real databases (neighbours reachable, out-links-only → undirected + shared-source): Strahlenschutz 153 → 220, Investing 37 → 166, KI 77 → 298 (KI: every page now reaches at least one neighbour, up from 26 of 44).

### Reading originals in Deep chat (`raw_read` under run memory)

Inside a Deep chat run, `tools.raw_read` decides *what* to serve in code, so a weak model cannot
loop on the table of contents (memo: [ideas/deep-chat-read-memory-and-section-grounding.md](../ideas/deep-chat-read-memory-and-section-grounding.md)).
Every served unit is marked in the visited-set under its usual key; a section's key uses the
anchor it resolves to (`§62` and `§ 62` are one entry).

| Request | Served |
|---|---|
| `file § N` / `file ## heading` | That section, with a `References:` footer. |
| Bare name of a long law (`§` anchors, > 16,000 chars), offset 0 | **Section map:** the 1–2 unread sections that best match the run's question plus its searches (`lex_index.query(…, scope="raw", sources=[file])`) in full, and the section titles ±5 around them. Without an index or a hit: byte window 0. |
| Bare name, other files / explicit `offset` | That byte window (pagination honoured). |
| A repeat of anything already read | **Auto-advance:** an unread section a footer offered, else the best-ranked unread section, else the next unread byte window, labelled `[memory: repeat of step N → …]`. Only a fully read file gets the stub `[memory] … fully explored for this question`. |
| An offset past the end | Clamped: the next unread window, labelled with the file's length; the bad offset is not remembered. |

**Reference footers (`src/refs.py`, pure).** `find_refs` finds `§ N` / `§§ N bis M` (expanded,
≤ 5) / `Anlage N` / `Artikel N` and the work named right after them (`der StrlSchV`, `des
Atomgesetzes`, `AtG`). `tools._resolve_work` maps the name to a file **inside the search scope
only** (a file of a level out of scope is never named): the version in force by the DB's
ontology (`ontology_query.resolve` + `ontology_time.current_expression`), else a raw file whose
stem or first heading names it. A § without a work name points into the same file; an
unresolved law-like name is `(not in scope)`; a missing anchor is flagged, never guessed. The
footer shows each reference's status (`unread`, `read`, `same file, …`, `hop limit reached`)
and the exact call to follow the first unread one. **Hop budget:** a section reached through a
cross-file reference is one hop deeper (same-file references are free); after 3 hops, footers
stop offering cross-file references; each followed cross-file reference earns 2 agent turns,
capped by `CHAT_REF_BONUS_MAX` ([configuration.md](configuration.md)).
