Scope note: researched 2026-10-22. The upstream repo is now **archived / read-only** (GitHub API `archived: true`, last push 2026-08-10), so no upstream fixes will land after the project's pinned commit `d337ae32` (2026-07-25, v0.0.16). Several statements below come from reading the vendored copy in `src/vendor/open_deep_research/` (same code as upstream at that commit) and from a local check against the installed `langchain-ollama` 1.1.0; those are marked "[code]".

## 1. What the repo, issues and LangChain posts say about local/Ollama/small models, and the known failure modes

### Takeaway
Upstream's only official guidance is that the model "will need to support structured outputs and tool calling." Ollama is wired up via `init_chat_model("ollama:<model>")` and nothing else. The worst failures for this setup are silent ones, and every one of them is reachable at the pinned commit. ChatOllama drops `max_tokens` and gets no `num_ctx`. A child-researcher exception ends research as though it succeeded (`or True`). Ollama never raises a "token limit" error, so none of the truncation and retry paths ever fire. And if the supervisor answers with no tool call, research ends immediately.

### Cited Findings
- README: models must support structured outputs and tool calling; models are loaded via `init_chat_model()`; there are Ollama/OpenRouter instructions only in linked issues; the repo is archived — [README](https://github.com/langchain-ai/open_deep_research)
- Maintainer answer on Ollama: "just pass `ollama:model` … Note you will need tool calling"; a user's alternative is the OpenAI-compatible route `OPENAI_API_BASE=http://localhost:11434/v1`, `openai:qwen3:30b-thinking` — [#166](https://github.com/langchain-ai/open_deep_research/issues/166), [#121](https://github.com/langchain-ai/open_deep_research/issues/121)
- Through an OpenAI-compatible local server (vLLM), the supervisor fails with `"auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser` (Qwen3-32B). Forcing `tool_choice="required"` gave tool calls with no ids. This is an open issue — [#190](https://github.com/langchain-ai/open_deep_research/issues/190)
- **`or True` bug:** in `supervisor_tools`, `if is_token_limit_exceeded(e, …) or True:` means *any* exception in a child `ConductResearch` run ends the research phase "as if research had completed normally". The graph then goes on to `final_report_generation` with whatever notes exist. Open bug, with an unmerged fix PR — [#283](https://github.com/langchain-ai/open_deep_research/issues/283), [PR #185](https://github.com/langchain-ai/open_deep_research/issues/185), [PR #286](https://github.com/langchain-ai/open_deep_research/issues/286). [code] Still present at vendored `deep_researcher.py` line 334.
- `compress_research` checks token-limit errors against `research_model` instead of `compression_model`, so a mixed-model setup gives "Maximum retries exceeded" — [PR #335](https://github.com/langchain-ai/open_deep_research/issues/335), [PR #230](https://github.com/langchain-ai/open_deep_research/issues/230). On token overflow, `remove_up_to_last_ai_message` removes the *most recent* context, not the oldest — [#252](https://github.com/langchain-ai/open_deep_research/issues/252), [PR #255](https://github.com/langchain-ai/open_deep_research/issues/255)
- If compression fails 3 times, `compressed_research` becomes the string `"Error synthesizing research report: Maximum retries exceeded"`. That string is passed on as a finding, while `raw_notes` still holds the tool output — [code: deep_researcher.py `compress_research`](https://github.com/langchain-ai/open_deep_research/blob/d337ae32ed4ff8f4c6fbe192ba3bf1b2d6610799/src/open_deep_research/deep_researcher.py)
- Final report on a token-limit error: the code truncates findings to `model_token_limit*4` chars only if the model is in `MODEL_TOKEN_LIMITS`. Otherwise it returns `"Error generating final report: Token limit exceeded, however, we could not determine the model's maximum context length…"`. [code] The map lists only a few `ollama:` entries (codellama, llama2, mistral, …) and no gemma.
- The compression prompt contradicts itself on the format of the Sources section (`**List of All Relevant Sources**` vs `### Sources`), which hurts determinism. This is in a vendored prompt and cannot be edited — [#232](https://github.com/langchain-ai/open_deep_research/issues/232), [PR #301](https://github.com/langchain-ai/open_deep_research/issues/301)
- Community PR "provider-friendly research fallbacks": a structured-output fallback for providers without reliable native structured output, and making webpage summarization and think-tool use opt-in. This confirms these are the weak points with non-OpenAI providers. Not merged — [PR #279](https://github.com/langchain-ai/open_deep_research/issues/279)
- Token bloat: raw web text accumulates in `researcher_messages`. By iteration 3, researchers re-read 30k+ input tokens per turn. This is a proposal with self-reported numbers, so treat it as anecdotal — [#296](https://github.com/langchain-ai/open_deep_research/issues/296)
- [code] Supervisor exit: research ends when `research_iterations > max_researcher_iterations`, **or the supervisor message has no tool calls**, or `ResearchComplete` is called. A small model that replies in prose instead of calling `ConductResearch` therefore ends research on turn 1 with empty notes. That is the "empty report" path, not "never calls ResearchComplete". The reverse risk ("never completes") is bounded by `max_researcher_iterations` (supervisor) and `max_react_tool_calls` (researcher) — [deep_researcher.py](https://github.com/langchain-ai/open_deep_research/blob/d337ae32ed4ff8f4c6fbe192ba3bf1b2d6610799/src/open_deep_research/deep_researcher.py)
- [code, verified locally] `ChatOllama(model=…, max_tokens=123)` leaves `num_predict=None` and `num_ctx=None` (langchain-ollama 1.1.0). So the `*_model_max_tokens` Configuration fields **do nothing** for `ollama:` models, and no context window is sent.
- Ollama's default context length depends on VRAM: under 24 GiB → 4k, 24–48 GiB → 32k, 48 GiB or more → 256k. Ollama recommends at least 64k for "web search, agents" and setting it with `OLLAMA_CONTEXT_LENGTH` — [Ollama docs: context length](https://docs.ollama.com/context-length). Open WebUI warns that a client-side `num_ctx` silently overrides the server value — [Open WebUI](https://docs.openwebui.com/getting-started/quick-start/connect-a-provider/starting-with-ollama)
- [code] The project's pinned daemon (`src/ollama_server.py`) sets `OLLAMA_NUM_PARALLEL=1` but **not** `OLLAMA_CONTEXT_LENGTH`. The rest of the app sends `num_ctx=INGEST_NUM_CTX` (32768). `docs/configuration.md` notes that "a different `num_ctx` makes Ollama reload the model". Deep-research calls therefore run at the server default context and may force a model reload whenever they alternate with app calls.
- Gemma 4 E4B tool calling on Ollama has these community reports: tool calls routed into the reasoning field with empty content (ollama#15241); parser "invalid character" errors that were still open as of Ollama v0.20.1; and a write-up calling E2B/E4B "too weak for reliable multi-step tool calling" — [OpenCode #20995](https://github.com/anomalyco/opencode/issues/20995), [Gemma 4 in Codex CLI](https://codex.danielvaughan.com/2026/04/10/gemma-4-local-model-codex-cli). Under long context, Gemma 4 malforms its own tool calls and then loops — [HF forum](https://discuss.huggingface.co/t/gemma-4-bug-fixes-and-research-request/176979). These are community-grade sources and may be fixed in later Ollama releases.
- Ollama structured output is grammar-constrained on the JSON schema, but property `description`s are ignored, and adherence varies by model — [Arize community](https://community.arize.com/x/phoenix-support/dqnqcxfn6k0e/troubleshooting-ollama-issues-with-structured-outp)
- LangChain's design notes: multi-agent is used only for research, never for parallel section writing ("disjoint" output). The final report is one shot. Context is compressed at each boundary (brief, then per-researcher compression). Raw tool results made the agent "prone to running into context window limits". The post gives no advice on smaller models or on splitting models by role — [LangChain blog](https://www.langchain.com/blog/open-deep-research)

### Inferences
- Do these first, because they are config-free or wrapper-level fixes for silent failures:
  1. **Give the deep-research model its own Ollama alias** with `PARAMETER num_ctx 32768` (same as `INGEST_NUM_CTX`, so no reload) and `PARAMETER num_predict <N>`, built from a Modelfile. Pass it as `ollama:<alias>` in Configuration. This is the only route that changes ChatOllama context and output length without touching vendored code. Alternative: set `OLLAMA_CONTEXT_LENGTH=$INGEST_NUM_CTX` in the pinned daemon's env (a change to `src/ollama_server.py`, not to vendor code).
  2. **Detect silent failure in the wrapper.** Treat the run as failed (fall back to Quick) when any of these hold: `notes` is empty or no `raw_notes`; any `compressed_research`/note starts with `"Error synthesizing research report"`; the report starts with `"Error generating final report"`; or the report cites fewer than N distinct URLs that also appear in `raw_notes`. The project already tests one prefix (AGENTS.md). Extend it to the compression prefix and to a minimum of zero research units.
  3. Ollama overflows by truncating the prompt silently, not by raising. So `is_token_limit_exceeded` will never fire, and no truncation path upstream will help. The only defence is to keep prompts under `num_ctx` by budget: low `max_react_tool_calls`, low Tavily `max_results`, and a short `max_content_length`.
- `max_structured_output_retries` (default 3) retries the clarify, brief and summary structured calls and the supervisor tool-binding. Raising it to 4–5 costs time only on failure, so it is cheap insurance for a 4B model.

### Gaps
- I did not find an upstream issue showing a full successful run with a ~4B model, and no published numbers for open_deep_research with any local model.
- I could not confirm whether Ollama v0.2x still truncates silently or now errors on overflow for the chat endpoint. This needs a local test (send a prompt larger than `num_ctx`, inspect the daemon log for "truncating input prompt").
- I did not confirm that Gemma 4 E4B's `ollama` template issues are fixed in the Ollama version on this box.

## 2. Recommended config values (speed vs quality) and which roles benefit from a stronger model

### Takeaway
Upstream's own benchmark shows that the research (supervisor/researcher) model matters most for quality: swapping only that model moved RACE from 0.4309 to 0.4943. Summarization stays on the cheapest model in every published configuration. With one local GPU and `OLLAMA_NUM_PARALLEL=1`, concurrency above 1 buys nothing, so spend the latency budget on fewer, more focused units and cap tool calls.

### Cited Findings
- Upstream defaults: summarization `gpt-4.1-mini`, research/compression/final-report `gpt-4.1`. Deep Research Bench RACE: defaults 0.4309 ($45.98, 58M tokens); research=`gpt-5` 0.4943 (204M tokens); research=Claude Sonnet 4 0.4401; the DRB submission (summarization=`gpt-4.1-nano`) 0.4344 (207M tokens) — [README](https://github.com/langchain-ai/open_deep_research)
- [code] Defaults: `max_concurrent_research_units=5`, `max_researcher_iterations=6`, `max_react_tool_calls=10`, `max_structured_output_retries=3`, `max_content_length=50000` chars (Tavily raw content passed into each summary call), `summarization_model_max_tokens=8192`, others 8192–10000 — [configuration.py](https://github.com/langchain-ai/open_deep_research/blob/d337ae32ed4ff8f4c6fbe192ba3bf1b2d6610799/src/open_deep_research/configuration.py)
- [code] Project wrapper today: `DEEP_RESEARCH_CONCURRENCY=1`, `MAX_ITERATIONS=4`, `MAX_TOOL_CALLS=6`, `MAX_TOKENS=8192` (ineffective with ChatOllama, see §1), clarification off, the same model for all four roles (`src/deep_research_agent.py`).
- [code] The summarization step runs once per unique URL in each `tavily_search` call, in parallel, each with a 60 s `asyncio.wait_for` timeout. On timeout or error it falls back to Tavily's short `content` snippet — [utils.py](https://github.com/langchain-ai/open_deep_research/blob/d337ae32ed4ff8f4c6fbe192ba3bf1b2d6610799/src/open_deep_research/utils.py)
- Context isolation per sub-agent is the main reason for the multi-agent design. A single agent "would naturally research each topic less deeply" — [LangChain blog](https://www.langchain.com/blog/open-deep-research)

### Inferences
- **Concurrency = 1–2.** With `OLLAMA_NUM_PARALLEL=1` the researchers serialise at the daemon anyway. Higher values only add queued summary calls that can hit the 60 s summary timeout and silently degrade to snippets. Keep 1, or 2 if the supervisor tends to split into 2 good topics. Overflow calls beyond the cap get an error tool message, which confuses small models.
- **`max_researcher_iterations` = 2–3.** It counts supervisor turns; one turn can spawn several units. Small models gain little from later rounds, and each round adds a full researcher plus compression pass.
- **`max_react_tool_calls` = 4–5.** It is the per-researcher budget, and each step adds about 5 summarised sources to context. At 32k ctx this is the main overflow lever.
- **`max_content_length` 50000 → about 12000–20000 chars.** Each summary call then fits comfortably in a 32k context (one ~4B model summarising 50k chars, ~12k tokens, is slow and quality drops). This is the single biggest latency lever, because summaries are about 5 × steps × units calls.
- **Role split.** Under a no-cloud constraint, the "stronger model" options are a larger local model, if one fits on the GPU next to E4B (or swapped in), for `final_report_model` first and `compression_model` second. Reasoning: compression and final report are single long-context synthesis calls, with no tool-calling and no schema, where small models lose citation fidelity. The research model needs reliable tool calling. Summarization can stay E4B, or be removed entirely (see §3). Upstream's data shows the *research* role has the biggest effect on RACE, but with E4B the binding constraint is tool-call reliability, so check E4B's tool-call success rate before spending budget there. Note the GPU rule (one card, no splits; AGENTS.md) and model-swap latency: a second model is only worth it if both stay resident.
- `allow_clarification=False` (already set). It avoids a structured-output call and an interactive stop.
- Raise `max_structured_output_retries` to 4–5 (see §1).

### Gaps
- No published ablation of open_deep_research with small or local models per role; the role recommendations above are inferred from upstream's GPT/Claude table and from the call types.
- No measured wall-clock numbers for E4B on this box; the ~1.2x budget has to be checked with a local benchmark.

## 3. Tavily knobs and skipping the summarization step

### Takeaway
At the pinned commit the vendored `tavily_search` tool hard-codes `include_raw_content=True`, `max_results=5` and `topic="general"`, and never sets `search_depth` (so Tavily's `basic` applies), `chunks_per_source`, `time_range` or domain filters. The model cannot change these either (`InjectedToolArg`). Changing them, or skipping the per-URL summarization, is impossible through `Configuration` alone. It needs `search_api="none"` plus an MCP-provided search tool, or a runtime monkeypatch that the project's vendoring rule effectively forbids.

### Cited Findings
- [code] `tavily_search(queries, max_results=5, topic="general")` calls `tavily_search_async(..., include_raw_content=True)`. It dedups URLs **within a single call only**, summarises each `raw_content[:max_content_length]`, and returns `--- SOURCE i: title --- URL: … SUMMARY: …` — [utils.py](https://github.com/langchain-ai/open_deep_research/blob/d337ae32ed4ff8f4c6fbe192ba3bf1b2d6610799/src/open_deep_research/utils.py)
- [code] Tool loading: `get_all_tools` gives `[ResearchComplete, think_tool]` + the search tool for `search_api` (`tavily`/`openai`/`anthropic`/`none`) + MCP tools from `mcp_config` (optionally with `mcp_prompt`). So `search_api="none"` plus a local MCP server exposing a custom `web_search` is a Configuration-only way to replace the search tool.
- Tavily Search API (current docs): `search_depth` is `basic` (default, 1 credit), `advanced` (2 credits, "highest relevance, but highest latency"), `fast` (1 credit, "lower latency with good relevance") or `ultra-fast` (1 credit, one NLP summary per URL). `chunks_per_source` is 1–3 (default 3) and applies to advanced/basic/fast. `max_results` is 0–20 (default 10). `include_raw_content` accepts `true`/`markdown`/`text` (`text` may add latency). `topic` is general/news/finance. `time_range` is day/week/month/year, plus `start_date`/`end_date`. `include_domains` (max 300) has `include_domains_mode` `restrict`/`prefer`; `exclude_domains` max 150. `auto_parameters` may silently switch to `advanced` (2 credits). Also available: `include_answer`, `language` + `filter_by_language`, `exact_match`, `include_published_date` — [Tavily Search API reference](https://docs.tavily.com/documentation/api-reference/endpoint/search)

### Inferences
- **Option A (Configuration-only, no new code path inside the graph):** keep Tavily but cut summary cost with `max_content_length` of about 12–20k. This is the cheapest change and the only one that respects "Configuration only" strictly.
- **Option B (custom search tool via MCP, `search_api="none"` + `mcp_config`):** a small local MCP server exposing `web_search(queries)` that calls Tavily with `search_depth="advanced"` (or `fast`), `chunks_per_source=3`, `include_raw_content=False`, `max_results=4–5`, and optionally `time_range`, `language="de"`, or `include_domains` with mode `prefer` for legal/official domains. It returns Tavily's relevance-ranked **verbatim chunks**, with URL and title, and does no LLM summarization. Expected effect:
  - It removes about 5 LLM calls per search step, the dominant latency term for a 4B model.
  - It replaces abstractive summaries, where small models paraphrase and hallucinate, with extractive quotes. That should improve citation accuracy (FACT C.Acc, as measured, rewards claims supported by the cited URL).
  - It keeps a global seen-URL set across calls, which is the cross-call dedup upstream lacks.
  - Cost: `advanced` = 2 credits per query.

  Constraints: the project already requires MCP deps (`langchain-mcp-adapters`, `mcp` are in `pyproject.toml` per `src/vendor/README.md`). The MCP server is a local process, so it does not violate "no second service" in spirit only if run in-process or stdio; check against AGENTS.md before adopting. Citations: the project parses URLs out of `raw_notes`, so the MCP tool output must keep the `URL: …` line format.
- **Option C (monkeypatch `utils.tavily_search_async` from `deep_research_agent.py`):** technically works, but it changes vendored behaviour by a route other than Configuration, contrary to the AGENTS.md rule. Not recommended without the user's approval.
- `topic="news"` and `time_range` matter only for time-sensitive questions. The tool cannot choose them per query (they are injected), so with Option B the wrapper could decide them in code from the brief (for example, a year in the question leads to `start_date`).

### Gaps
- I found no published measurement of Tavily `basic` vs `advanced` vs `fast` latency in milliseconds, or of chunk quality vs raw-content summarization. Tavily's docs give only qualitative latency ordering.
- I did not verify whether the MCP path in the vendored `load_mcp_tools` requires `auth_required`/an HTTP URL (vs stdio). Read `utils.py:load_mcp_tools` before choosing Option B; it may only support streamable-HTTP MCP servers.

## 4. Published evaluations (Deep Research Bench RACE/FACT) and what drives the scores

### Takeaway
Deep Research Bench (100 PhD-level tasks, RACE for report quality and FACT for citations) puts open_deep_research at RACE 0.43–0.49 with GPT-4.1/GPT-5. That is close to the top commercial agents, but there are no small-model entries. The best results from small open models (an 8B model and Qwen3-30B-A3B) come from **outline-driven, section-by-section writing over a curated evidence memory**, and every one of them is a trained model, so their scores do not carry over to prompting a 4B model.

### Cited Findings
- DRB design: 100 tasks (50 EN, 50 ZH), 22 fields. RACE scores comprehensiveness, insight/depth, instruction-following and readability against reference reports (Gemini-2.5-Pro judge). FACT extracts statement–URL pairs and checks support: citation accuracy (C.Acc) and effective citations per task (E.Cit) — [DRB paper](https://arxiv.org/html/2506.11763), [README](https://github.com/langchain-ai/open_deep_research)
- DRB Table 1 (2025): Gemini-2.5-Pro Deep Research RACE 48.88 / C.Acc 81.44 / E.Cit 111.21; OpenAI DR 46.98 / 77.96 / 40.79; Perplexity DR 42.25 / 90.24 / 31.26; Claude-3.7-Sonnet w/Search 40.67 / 93.68 / 32.48; GPT-4.1-mini w/Search 30.26 / 84.58 / 4.35. High accuracy with few citations is common for simple search-LLMs, so volume and precision trade off between agents — [DRB paper](https://arxiv.org/html/2506.11763)
- open_deep_research ranked #6 on the DRB leaderboard at 0.4344 (Aug 2025). The leaderboard's current status is unclear; sources conflict on whether it is still live — [rywalker.com summary](https://rywalker.com/research/open-deep-research), [README](https://github.com/langchain-ai/open_deep_research)
- AgentCPM-Report (8B, arXiv 2602.06540): DRB RACE overall 50.11 (Insight 52.64, Readability 44.17), vs Gemini-2.5-Pro-DR 49.71 and OpenAI-DR 46.45. Its WARP method: a sparse level-1 outline, then per-section query → retrieve → draft, then periodic "deepen" (expand a section or stop), capped at 12 expansions, with quality plateauing at about 9. A prompt-only WARP on Qwen3-235B scored 50.72 vs plan-then-write 49.90. The paper names these small-model weaknesses: comprehensive outlines, deciding when to stop, and inline tables/figures — [AgentCPM-Report](https://arxiv.org/html/2602.06540)
- Same table: WebWeaver (Qwen3-30B-A3B) 46.77; WebThinker-32B-DPO Comp 39.40 / Insight 35.40; DR Tulu-8B Comp 41.70 / Insight 41.80; WebShaper-32B 34.93 — [AgentCPM-Report](https://arxiv.org/html/2602.06540)
- WebWeaver (ICLR 2026): a planner alternates evidence gathering with outline revision, linking outline sections to a memory bank of evidence. A writer then retrieves *only the cited evidence per section* and writes section by section, which reduces long-context problems and citation hallucination. It reports the highest E.Cit and C.Acc on DRB FACT — [WebWeaver arXiv](https://arxiv.org/html/2509.13312v3), [ICLR page](https://iclr.cc/virtual/2026/poster/10009906)
- FINDER/DEFT failure taxonomy (~1,000 reports, 14 failure modes): agents struggle less with task comprehension than with "evidence integration, verification, and reasoning-resilient planning" — [arXiv 2512.01948](https://arxiv.org/abs/2512.01948)

### Inferences
- What drives the scores: RACE comprehensiveness and insight come from a good outline and per-section evidence. FACT C.Acc comes from writing claims next to verbatim evidence. E.Cit comes from source breadth, i.e. more distinct URLs actually used. A 4B model's single-shot `final_report_generation` over long compressed notes is weak on all three: lost-in-the-middle, and paraphrase drift in citations.
- E4B scores cannot be predicted from these numbers. Expect to land well below the 0.43 of GPT-4.1, and measure locally instead (see Gaps).

### Gaps
- No DRB/RACE/FACT results found for any ~4B model, for Gemma 4, or for open_deep_research with local models.
- I could not open the DRB leaderboard's 2026 state; it may have new entries.
- I did not read DEFT's per-category frequencies (abstract only).

## 5. Generic deep-research tweaks that suit small models (and how to apply them from outside the vendored graph)

### Takeaway
The literature points the same way for small models: fewer and narrower sub-questions; extractive, quote-preserving evidence instead of abstractive summaries; outline first, then section-by-section writing with only that section's evidence; and citation checking in code. In this project, the graph's research phase can be steered only through Configuration and the input message. Everything from outline onward can be done *after* the graph, in the wrapper, using `raw_notes` and `notes` as the evidence pool.

### Cited Findings
- Outline-first plus per-section evidence-scoped writing beats plan-then-write and single-shot synthesis (WARP +0.8 RACE overall at 235B, prompt-only). Expansions plateau at about 9 steps — [AgentCPM-Report](https://arxiv.org/html/2602.06540)
- Retrieving only the evidence cited for each section reduces citation hallucination and long-context failures — [WebWeaver](https://arxiv.org/html/2509.13312v3)
- open_deep_research's own lesson: do not parallelise *writing* across agents (disjoint output); compress at each boundary — [LangChain blog](https://www.langchain.com/blog/open-deep-research)
- Evidence integration and verification are the dominant failure areas — [DEFT/FINDER](https://arxiv.org/abs/2512.01948)
- Tavily `chunks_per_source` returns up to 3 relevance-ranked snippets per URL, suitable as verbatim evidence — [Tavily docs](https://docs.tavily.com/documentation/api-reference/endpoint/search)

### Inferences
Concrete tweaks, ordered by value per latency. Each is marked as Configuration-only (C) or as wrapper/post-processing in `src/deep_research_agent.py` (W):
1. (W) **Narrow the input.** `DEEP_RESEARCH_QUESTION` should ask for at most 2–3 sub-topics, each a one-line question. The brief node rewrites it anyway, but the brief and the supervisor take cues from the message. Fewer units mean less context and less compression.
2. (C) **Use the budgets from §2**: concurrency 1–2, iterations 2–3, react calls 4–5, `max_content_length` 12–20k, retries 4–5, and a Modelfile alias pinning `num_ctx` and `num_predict`.
3. (W) **Validate citations in code after the graph.** Extract `[n]`/URL pairs from the report and keep only URLs present in `raw_notes`. Optionally check that each cited sentence shares salient tokens or numbers with that URL's summary or snippet, using lexical overlap with no LLM. Drop or flag unsupported citations and renumber `### Sources`. This targets FACT C.Acc directly and costs about 0 s. It works around the `### Sources` format conflict (#232).
4. (W) **Rewrite the report as outline then per-section** (replaces upstream's single-shot report; adds roughly N section calls). Use `notes`/`raw_notes` as the evidence pool. Code builds an outline, either a 1-call LLM outline (level-1 headings only, per WARP) or one section per research unit. For each section, code selects the top evidence blocks (URL + summary/snippet) by lexical overlap with the section title. The model writes the section with only those blocks and must cite as `[URL]`; code maps the URLs to numbers. To stay within 1.2x latency, skip upstream's `final_report_generation`, which is not possible via Configuration (it always runs). Alternatively, use the upstream report as the draft and only regenerate sections that fail the citation check. Realistic budget: use this *instead of* Quick-mode fallback polishing, not in addition.
5. (W) **Dedup URLs across researchers**: merge `raw_notes` blocks by URL before reuse and keep the longest summary. Upstream dedups only within one search call.
6. (W/C) **Extractive evidence**: either Option B in §3 (Tavily chunks, no summariser) or, in post-processing, prefer quoting numbers and dates verbatim from snippets. Small models' abstractive summaries are the main citation-drift risk.
7. (W) **Treat these as failures and fall back to Quick**: no `ConductResearch` executed (empty notes), the compression error string, report error strings, fewer than 3 distinct verified URLs, or a report shorter than K words. This is consistent with the project's existing Quick fallback gate (≥600 words, ≥4 URLs).
8. (C) Leave `think_tool` as is, since it cannot be removed via Configuration. Note that PR #279 makes it limited or opt-in because weak models waste turns on it; a smaller `max_react_tool_calls` bounds that waste.

### Gaps
- No published experiment applies these tweaks to open_deep_research with a ~4B model. The quality and latency effects above are inferred from larger-model papers and from the code's call structure.
- Before adopting tweak 4, a local A/B is needed on a fixed question set measuring wall-clock time, distinct verified URLs, and unsupported-citation rate, to confirm it fits within 1.2x.
